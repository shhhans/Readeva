# 架构

## 进程模型

```
┌────────────────────┐    HTTP (同源默认)     ┌──────────────────────────┐    HTTP (地址可配置)    ┌────────────────────────┐
│  浏览器应用 (web/)  │ ─ 静态页面 + /api/* ─▶ │  Readeva 服务 (server/)   │ ─ 单页字节流 / 结果 ──▶ │ Docling 解析服务        │
│  原生 ES Modules   │ ◀── JSON / PDF 字节流 │  Node.js + Express        │ ◀── DoclingDocument ── │ (docling_service/,      │
│  + PDF.js 渲染     │                       │  书库 / 解析编排 / 数据    │                       │  Python+FastAPI)        │
└────────────────────┘                       └──────────────────────────┘                        └────────────────────────┘
```

- 客户端是浏览器应用，由 Readeva 服务静态托管（默认同源）；关闭浏览器不影响两个服务进程。
- Readeva 服务是独立进程，监听地址/端口可配置（CLI 参数或环境变量，见 README「配置」）。
- **Docling 解析服务**（Issue #3）是另一个独立进程（本机用 conda 环境 `readeva` 运行）：无状态，接收单页 PDF 字节流、返回结构化内容；地址在 Readeva 服务端配置（`--docling-url` / `READEVA_DOCLING_URL`），**客户端不接触解析服务地址与密钥**。
- 客户端可在「服务设置」中指向其他 Readeva 服务地址（localStorage）；所有契约不依赖客户端与服务共享文件路径——导入上传字节流，阅读按 HTTP URL 取回 PDF 副本，**页解析由 Readeva 服务抽取单页后以字节流发送**。
- 解析服务实现 docling-serve 兼容线协议（异步提交/状态轮询/结果获取），可被远端 docling-serve 或解析项目的正式服务替换；解析内容质量修复由解析项目承担，本项目只消费结果。

## 数据模型

文档身份以**文件内容 SHA-256 摘要**确定（`server/library.js`）：

- 导入时计算摘要；`library/<sha256>.pdf` 为内容寻址副本，同一内容永不重复入库（导入幂等）。
- 文档名只是元数据：改名再导入仍返回同一文档（`created: false`）。
- 阅读位置按文档保存在 `progress/<sha256>.json`，变化后立即原子写入；服务端为真源，客户端打开文档时从服务取回恢复。
- **页解析（Issue #3）按「文档身份 + 页码」保存在 `parses/<sha256>/page-N.json`**：记录解析身份（`parseId`，对内容块做 SHA-256，内容不变则身份不变）、按阅读顺序的内容块（结构、文字、资源、可用位置）及元信息/失败原因；服务重启后直接取回，不重新解析。
- **译文（Issue #8）按「文档身份 + 页解析身份」保存在 `translations/<sha256>/<parseId>.json`**：每条译文绑定来源（块 id 或归一化选文 sha256）与目标语言；翻译完成自动持久保存（事务式：成功才写入），服务重启后直接取回；页解析被替换（新 parseId）后旧译文不再出现在查询结果里。

JSON 持久化使用「临时文件 + rename」原子写；Windows 上 rename 可能因文件句柄冲突抛 EPERM/EBUSY，实现中带有限重试（`server/fs-utils.js`）。

## 内容块模型（页解析）

解析服务返回 DoclingDocument JSON（docling-core 序列化格式），服务端适配层（`server/docling.js`）按 body 子节点顺序规范化为内容块：

| 块类型 | 来源 | 字段 |
| --- | --- | --- |
| `heading` | `title` / `section_header` | `text`、`level` (1/2) |
| `paragraph` | `paragraph`、`text`、`caption`、`footnote` 等 | `text` |
| `list` | `list_item`（相邻合并，含 list 组） | `items[]`、`ordered` |
| `table` | `table`（grid 解引用 table_cells） | `rows[][]`、`columnHeader` |
| `image` | `picture`（内嵌 data URI 或 http(s) URI） | `image.uri`、`image.mimeType` |

- 每块携带 `id`（块内唯一）与阅读顺序 `order`；页眉页脚（furniture 层与 page_header/page_footer/page_number）不进入阅读顺序。
- 位置取自 `prov[0].bbox`（记录 l/t/r/b/coordOrigin，页码归一为用户阅读页）；**缺少位置不阻断展示**，仅 `bbox: null`。
- 坐标为 PDF 点距（页面尺寸坐标系，`coordOrigin` 记录原点方向：Docling 默认 `BOTTOMLEFT`，PDF 原生；也兼容 `TOPLEFT`）；客户端换算时按原点显式翻转（见「双向联动」）。
- 图片资源仅接受 data URI 或 http(s) URI；服务端本地路径等不可达资源以占位展示，内容块仍然保留。
- 解析身份 `parseId = sha256(blocks)`：同一内容重新解析身份不变（为后续译文绑定提供稳定关联）。

## API

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/api/health` | 健康检查 `{ ok, service, version }` |
| POST | `/api/documents/import` | 原始字节流上传（`x-filename` 头携带文件名）；校验为可解析 PDF；成功返回 `{ document, created }`，201 新建 / 200 已存在（相同内容） |
| GET | `/api/documents` | 列出全部文档（按最近阅读排序） |
| GET | `/api/documents/:id` | 单个文档元数据 |
| GET | `/api/documents/:id/file` | PDF 副本字节流（不可变缓存头） |
| GET | `/api/documents/:id/progress` | 阅读位置 `{ page, zoom, updatedAt }`（无记录时默认第 1 页、100%） |
| PUT | `/api/documents/:id/progress` | 保存阅读位置；页码按 PDF 页数钳制，缩放钳制到 [0.25, 5] |
| GET | `/api/parse/service` | 解析服务可用性 `{ configured, engine }`（不含地址/密钥） |
| POST | `/api/documents/:id/pages/:page/parse` | **页解析请求**（幂等，兼作失败页显式重试）：未开始 → 202 后台解析；并发占满 → 202 `{status:"queued"}` 排队且置于队首；进行中 → 200；已完成 → 200 `{ reused: true }` 复用不重新解析；未配置解析服务 → 503 |
| GET | `/api/documents/:id/pages/:page/parse` | **任务状态**：`idle`（未开始）/ `queued`（已接受、队列中）/ `running`（已开始）/ `succeeded`（含 `parseId`）/ `failed`（含 `error`） |
| GET | `/api/documents/:id/pages/:page/parse/result` | **结果获取**：按页返回 `{ parse: { parseId, blocks, meta } }`；仅成功后可得，否则 404 |
| PUT | `/api/documents/:id/reading-position` | **阅读页优先级更新**（Issue #5）：`{ page }` → 服务端按「当前页及后续页优先，其余降级」重排未开始任务（显式请求置顶的页不降级），返回调度后的整本进度快照；未配置解析服务时 `{ scheduled: false }` |
| GET | `/api/documents/:id/parse/progress` | **整本解析进度**（Issue #5）：逐页状态（idle/queued/running/succeeded/failed + `queuePosition` + 失败原因）+ 计数（succeeded/failed/running/queued/idle、total）；基于轻量状态索引构建（B1：不逐轮读盘解析内容块），服务重启后进度不丢。**进度轮询同时作为客户端会话心跳**（Issue #6） |
| GET | `/api/documents/:id/session` | **客户端会话状态**（Issue #6）：`{ documentId, supported, lastSeen, graceMs, expired }`；**只读观察端点，不刷新 lastSeen**（测试/诊断用）；未配置解析服务时 `{ supported: false }` |
| GET | `/api/dictionary/lookup?word=…` | **选词查词**（Issue #7）：ECDICT 离线英汉词条查询；200 `{ entry }`（词条/音标/中英释义/词性/柯林斯/牛津/考试标签/词频/词形变化）；未收录 404 `{error:"entry not found"}`；词典数据未准备 503；非法参数（缺 word/仅空白/超长）400 |

错误返回 `{ error }`；非 PDF 导入返回 400；未知文档返回 404；非法页码返回 400。

解析任务在服务端后台执行（`server/page-tasks.js`）：抽取单页字节流（pdf-lib，固定元数据保证字节确定）→ 提交解析服务 → 轮询状态 → 取结果 → 规范化 → 自动持久保存（成功与失败都落盘）。服务重启丢失的进行中任务回落为「未开始」，已完成页永远从磁盘取回。

## 按阅读位置的解析调度（Issue #5）

`server/page-tasks.js` 的 `ParseTaskManager` 在单页编排之上维护**按文档的未开始任务优先队列**（内存态；已开始/成功/失败状态仍以 parse-store 落盘记录为唯一状态源，不另存一份）：

- **优先级规则**：`PUT /api/documents/:id/reading-position` 上报阅读位置后，未开始任务按「当前页 → 后续页 → 前置页」升序重排；跳页只重排未开始任务，进行中的页不取消、不重复启动。
- **队列成员**：仅收未开始（无落盘记录且未运行）的页；已完成页从队列摘除、复用结果；**失败页不入自动队列、不自动重试**——标记失败、不阻塞队列，仅通过显式解析请求（`POST …/parse`）重试，成功后由 `saveResult` 替换失败记录。用户视角：整本补全会停在「解析 x/y · 失败 n」（面板头部静态文本，**失败只计数**、不列页码），失败页保持可见可重试。
- **派发**：全局并发上限可配置（`--parse-concurrency` / `READEVA_PARSE_CONCURRENCY`，默认 2，与 docling_service 线程池 `max_workers=2` 对齐——同进程共享已加载模型，内存不翻倍、CPU 翻倍；跨文档共享；本机 2GB pagefile 下 2 是稳妥上限）；任务结束（成功或失败）后继续派发队列下一页——队列按序补全其余未解析页（闲置补全）。跳页插队为 staggered 语义：新页插入队首，任一并发槽释放即开始，不做「保留空槽」，平均跳页等待约为串行的一半。
- **开局填充**：每次扫全会话（文档打开/首次阅读位置上报）立即填满所有并发槽（并发 2 → 两页同时开始，不做 pacing）；pacing 只作用于后续背景派发。会话在队列排空且无运行中任务时结束，下次上报重新授予。
- **动态 pacing（默认）**：连续背景派发之间的间隔 = 最近 3 页转换耗时（派发→succeeded/failed，不含排队）均值 × `--parse-sweep-pacing-factor` / `READEVA_PARSE_SWEEP_PACING_FACTOR`（默认 0.5），钳制 [0, 5000]ms——设备快→间隔小吞吐高，设备慢→间隔大留 CPU 给阅读交互（系数 >0.5 时并发 2 下出现 CPU 空隙）。**代价与边界**：pacing 默认开启，稳态整本补全吞吐低于「不节流」（单页耗时 T 时约 1.5T/页）；**pacing 状态按文档分桶**（每文档独立 `lastSweepDispatchAt` 与等待定时器，配合跨文档轮转：A 的间隔不挡 B 的派发）；**当前页豁免 pacing**（`updateReadingPosition` 记录的当前阅读页不被背景间隔拖住，翻页后新页立即派发——消除了「翻页最多等待一个 pacing 间隔」的旧代价）；**系数 0 = 不节流档**（关闭动态间隔，槽释放即派发；负数/非法值回落默认 0.5）；固定节流覆盖见下一行。耗时样本仍是服务级滚动估计（多文档并行时互相污染，待后续按 docId 分桶）。
- **固定节流覆盖（可选）**：`--parse-sweep-delay-ms` / `READEVA_PARSE_SWEEP_DELAY_MS` 设 >0 时以固定间隔覆盖动态 pacing（同样按文档分桶）。显式请求/置顶页/当前页在两种模式下均不受限（等待期间任务留在队首、不占并发槽）。
- **显式请求插队**：`POST …/pages/:page/parse` 将目标页置于队首并标记置顶（pinned）：随后的阅读位置重排不会把显式请求/重试的页降级；页离开队列（开始执行或复用跳过）即消耗置顶标记。
- **进度查询**：`GET /api/documents/:id/parse/progress` 返回逐页状态（含队列位置与失败原因）与计数（succeeded/total + failed/running/queued/idle）；已完成/失败页以落盘记录的轻量状态索引为准，服务重启后进度不丢。
- **轻量状态索引（B1）**：进度快照、优先级重排与单页状态查询经 `parse-store.getStatus()` 只读状态字段（status/parseId/error/updatedAt），按 mtime+size 命中缓存、写路径主动失效——不逐轮全量读盘解析内容块（实测 215 页 × ~660KB/页 从每轮 ~139MB 读盘 / ~0.3s 同步阻塞降至每轮仅 stat）；内容块仅在 `GET …/parse/result` 时读取。
- **触发边界与自愈**：整本调度仅由阅读位置更新触发（客户端打开文档/翻页时上报）；单独的页解析请求不触发整本调度（Issue #3 行为保持）。客户端退出宽限期处置与重连重新调度见 Issue #6 一节；作为低成本兑底，面板在事件式刷新整体进度快照时发现「无 queued/running 且仍有 idle 页」（如服务重启导致内存队列丢失）会自动重报阅读位置恢复调度（带冷却）。
- **前端呈现（收敛轮）**：右侧面板**不再有独立进度区**（逐页状态芯片已彻底移除）。单页解析状态、失败原因与显式重试**内联在内容列表**（状态徽标 + 失败原因 + 重试按钮）；整本进度只有**面板头部一处静态文本**（如「解析 12/215 · 失败 1」），在事件（派发/完成/失败/重试/翻页）时取一次快照更新，**阅读视图打开期间另以固定 8s 间隔慢刷新**（离开阅读视图即停止定时器；不引入秒级轮询、不重建逐页芯片）；未配置解析服务时界面无任何进度残留（仅一行静态提示）。
- **头部进度刷新与失败页取舍**：慢刷新只取整本快照并更新头部文本，**不触发自愈重排**（自愈仍由事件式刷新驱动，调度语义不变）；每次快照（事件式或慢刷新）后都重新计时 → 相邻两次快照间隔 ≥ 8s（事件刚刷新过不会紧接着重复取数），避免头部文本长期过期。**失败页只计数**：头部不列出失败页码列表（逐页失败详情可查 `GET …/parse/progress` 的 `pages[]`），失败详情在对应页的内容列表内联条目里（状态徽标 + 失败原因 + 显式重试按钮）——取舍理由：头部保持单行静态文本，不引入逐页芯片/可展开列表，避免重建 DOM 与滚动干扰阅读。

## 双向联动（Issue #4）

原页与内容块的对照阅读在纯前端实现（`web/page-linkage.js`），服务端无新增接口：

- **覆盖层**：`#page-stage`（position relative）包住 canvas，`#page-overlay` 覆盖层内按内容块 bbox 叠加定位框 `.page-block-box`。bbox（PDF 点坐标）→ 渲染坐标的换算系数取「canvas CSS 尺寸 / 页面点尺寸」，与 devicePixelRatio 无关，天然跟随缩放（含「适配宽度」）；`coordOrigin=BOTTOMLEFT` 时按页面点高度翻转后映射到顶部原点。
- **滚动布局契约**：`#viewer` 用 `justify-content: flex-start` + `align-items: flex-start`、`#page-stage` 用 `margin: 0 auto`——画布宽/高于可视区时只向右/向下溢出，起始侧始终可达（居中溢出会使起始侧落在可滚动区之外，scrollLeft/scrollTop 无法为负，主动定位会静默失效）；不拉伸 stage 保证覆盖层贴合 canvas 实际尺寸。
- **主动定位滚动**：直接设 `viewer.scrollTop/scrollLeft`（`#viewer`）与 `content.scrollTop`（右侧面板）居中目标元素，不用 `scrollIntoView`（可能连带滚动外层文档）。
- **组件间零耦合**：数据全部经 DOM 与事件流转——渲染完成后 `PdfViewer` 在 `#viewer` 上派发 `pdf-rendered`（携带 page/zoom/页面点尺寸）；`ParsePanel` 渲染内容后派发 `parse-blocks-changed`，内容块带 `data-bbox`（原始 bbox JSON）。联动层监听两类事件重建覆盖框，翻页/缩放后位置自动重算，选中态跨缩放保留、跨翻页重置。
- **双向交互**：悬浮右侧内容块 ↔ 悬浮原页覆盖框互相高亮（`.hot`）；点击右侧块 → 原页滚动定位到对应区域，点击覆盖框 → 右侧滚动定位到对应块（`.active` 选中态独占）。
- **失败语义**：位置不可用（`bbox: null` 或无效坐标，如零尺寸/出页）的内容块照常展示、无覆盖框；悬浮静默（无框可亮即无操作）；主动定位失败给 `#locate-toast` 短提示（约 3s 自动消失），均不报错、不打断阅读。

## 客户端会话、宽限期与重连恢复（Issue #6）

客户端是浏览器应用，由 Readeva 服务静态托管；**关闭浏览器不影响服务进程**——服务独立推进队列。本任务为「客户端退出/失联」补齐生命周期语义：

- **会话存续（心跳）**：客户端任何文档活动都刷新该文档的 `lastSeen`——阅读位置上报（`PUT reading-position`）、整本进度轮询（`GET parse/progress`，客户端阅读视图内 8s 慢刷新）、单页状态轮询、解析请求/结果获取、阅读位置保存等；服务端不区分「心跳」与业务请求，活动即活跳。会话按文档跟踪（队列也按文档隔离），切换文档后旧文档进入宽限期倒计时。
- **宽限期**：`--client-grace-ms` / `READEVA_CLIENT_GRACE_MS`，默认 300000ms（5 分钟）。**默认取 5 分钟是为浏览器隐藏标签节流留余量**：浏览器对隐藏标签页的页面内定时器节流（长时间隐藏后约 1 次/分钟），阅读视图内 8s 慢刷新心跳被稀释后，60s 宽限期可能误判到期；5 分钟 ≈ 5 个节流心跳的余量。**必须大于实际客户端心跳间隔**（前台 8s / 隐藏标签节流后 ~1 次/分钟）；非法值/0 回落默认。取舍：未采用「有 running 任务时延长宽限期」的替代方案——任何运行中期间的宽限顺延窗口都会让 pump 在运行页完成后派发下一页，闭浏览器的场景会排空整个队列而非「完成已开始页 + 清除未开始任务」，与验收 2 语义冲突（既有短宽限期用例必须保持绿色）；默认 5 分钟 + 节流心跳（~1/分钟）已覆盖隐藏标签场景，无需延长。
- **到期处置（幂等）**：周期性会话检查（250ms）发现文档超宽限期无活动即处置：**运行中的页不取消、继续跑完并落盘**（运行中页与队列清除无关）；**尚未开始的任务（队列/置顶标记）清除**，不派发；扫全会话与开局填充额度一并结束。处置幂等：重连/多次到期不误伤——已完成页保留、清除的页保持清除、零新增派发。
- **竞态收口**：派发路径（`takeNext`）在会话已超宽限期但周期检查尚未执行时立即处置并跳过该文档，消除「运行中页完成 → pump 派发下一页」与「到期清除」之间的竞态窗口；客户端在宽限期内的任何活动都会刷新 lastSeen 使到期不生效（宽限内回来队列不受影响）。
- **重连**：客户端重新打开文档（`showReader` 重新上报阅读位置）→ 服务端按当前阅读位置重新调度未完成页（复用 #5 的重排规则），已完成页从持久化取回、不重新解析；客户端既有的「无 queued/running 且仍有 idle 页」自愈逻辑同样可在会话恢复后重建队列。
- **执行路径归口项（本任务收口）**：
  - **按页抽取缓存**（`server/docling.js` 的 `PageExtractor`）：整本 PDF 只 `readPdf` + `PDFDocument.load` 一次并按文档缓存，页间复用（原实现每页全量加载整本 PDF）；文档不再有排队/运行中任务（含宽限期到期后运行中页全部完成）时释放缓存回收内存。与「断开后继续跑完已开始页」叠加：运行中的页在客户端退出后仍可完成，因整本只解析一次。
  - **图片 base64 体积评估**：Docling 内嵌图片以 data URI 落在页记录里，单页约近 1MB。评估结论：**保持现有对外契约与落盘格式**（`blocks[].image.uri` 为 data URI，接口与持久化格式不变）——单用户本地书库场景下 215 页 × 1MB ≈ 215MB/本（仅含图片页）可接受，且改造（转文件引用/压缩）会改变 #3 已锁定的接口契约与 B1 规模回归的记录形态，收益与风险不成比例；若未来远程部署成为瓶颈，可另立 Issue 评估「图片资源去重（跨页内容寻址）+ 文件引用」迁移，届时在 PR 中说明格式变更。
  - **跨文档取任务轮转（round-robin）**（`server/page-tasks.js` 的 `takeNext`/`setQueue`）：取走某文档队首后把该文档移到轮转尾部，下一次取任务从下一份文档开始——并发下不单个文档排空；新队列（新打开/重连的文档）插入轮转队首，优先获得派发轮次，已有队列的文档保持位置（翻页上报不反复插队饿死其他文档）。
  - **状态缓存随文档清理**：`ParseStore.pruneStatusCache` 在会话周期检查时剔除已不在书库中的文档缓存条目（statusCache/indexCache/lastSeen），与文档删除能力联动（删除未实现时保证缓存不无界增长）。
  - **冷启动状态索引（index.json）**：每文档 `parses/<sha>/index.json` 保存状态字段（status/parseId/error/updatedAt）+ 页文件 mtime/size 快照，保存路径按文档串行链增量更新（避免并发读-改-写丢条目）；`getStatus` 冷启动（内存缓存空）时先经索引取状态，**消除重启后首轮逐页读全量记录**（原 B1 首轮成本）；索引缺失/损坏（如测试直接落盘页记录）或条目与页文件 stat 不匹配（页文件被外部改动/删除）时回退逐页读盘，**正确性不依赖索引**（索引只是加速器）。

## 选词查词与 ECDICT 离线词典（Issue #7）

右侧解析原文选词 → ECDICT 离线英汉查询，交付「界面 → 服务 → 存储 → 测试」贯通的可演示行为：

- **数据准备（Hans 执行）**：`scripts/build-dictionary.mjs` 从 ECDICT 的 `ecdict.csv`（仓库单文件约 63MB）一次性构建到 `<数据目录>/dict/ecdict`（可用 `--ecdict-dir` / `READEVA_ECDICT_DIR` 覆盖）。产物 3 个文件：`ecdict.words.bin`（按小写键 UTF-8 字节序排序的内存索引，记录 `[keyLen u8][key][offset u32][length u32]`）、`ecdict.entries.jsonl`（每行一个词条 JSON，与索引同序）、`manifest.json`（来源、许可声明、统计，最后写入作完整性标记）。构建整体先写临时目录再原子换入，中断不残留半成品；同键（小写）去重保留首现词条；构建时把 ECDICT 字段内的字面 `\n` 行分隔符转换为真实换行（API 契约统一「以真实换行分行」）；`detail`（例句 JSON）与 `audio`（网络音频 URL）不入离线数据，保证断网可完整展示释义。
- **服务端查询（`server/dictionary.js`）**：首次查询惰性加载索引（~15MB）到内存，查询 = 内存二分查找 + 一次词条文件切片读取，**不访问网络**；解析服务不可用时查词照常工作。词典文件缺失视为「未准备」而非致命错误：返回 503 并给出明确提示，数据构建好后无需重启即可恢复（加载失败会重试）。查询词归一化：NFC、弯引号/破折号折算、连续空白折叠（支持词组词条）、去首尾标点（保留词条实际存在的撇号/连字符，如 `'hood`、`-gate`）、小写；空/超长（>80 字符）返回 400。
- **前端交互（`web/dictionary.js`）**：组件零耦合，监听 `#parse-content` 的选择（pointerup 后读取）与内容变化（`parse-blocks-changed`）事件；选中文本后浮现「查词」工具条（定位到选区上方，放不下时下方），点「查词」主动发起查询（不做自动弹窗）并消费选区（工具条不回弹）。结果停靠在面板底部卡片：词条、音标、考试标签芯片、中英释义（按行渲染）、词性占比、柯林斯星级/牛津核心/BNC 与词频序/词形变化；未收录、词典未准备、查询失败均明确反馈；卡片底部固定展示数据来源与许可（ECDICT · MIT License）。
- **边界**：首版不维护查词历史（服务端不留存、浏览器不写本地存储）；原文/选文翻译属 Issue #8，工具条结构预留扩展位。

## 选文与内容块翻译（Issue #8）

右侧主动翻译（默认目标语言中文），交付「界面 → 服务 → 存储 → 测试」贯通的可演示行为：

- **入口**：右侧解析原文选中文本 → 工具条「翻译」（`#7` 工具条预留的扩展位）；或内容块右上角「翻译」按钮整块翻译（标题/段落/列表/表格；图片等无文本块不提供）。翻译由用户主动触发，不做自动翻译。
- **服务端适配层（`server/minimax.js`）**：调用 **MiniMax 中国站（国内站）OpenAI 兼容接口** `https://api.minimax.cn/v1/chat/completions`，模型固定 `MiniMax-M3.1-Flash`（国内站文档模型名），`Authorization: Bearer <MINIMAX_API_KEY>`。**密钥只从服务端环境变量 `MINIMAX_API_KEY` 读取**，客户端不接触密钥与上游地址，接口响应/日志/错误信息都不携带密钥。国际站（api.minimax.io）不使用——密钥与模型订阅按站区分，默认值必须是中国站；`READEVA_MINIMAX_BASE_URL` 可覆盖（自动化测试指向 mock）。块源文本由服务端从解析记录自行提取（客户端只传块 id；列表按项合并、表格按行列拼接），保证译文与解析内容一致；选文归一化（NFC + 空白折叠 + 去首尾）后以 sha256 为来源键。M 系列模型的非流式响应可能内嵌 `<think>…</think>` 思考段，适配层剥后取正文。
- **译文存储（`server/translations.js`）**：按「**文档身份 + 页解析身份（parseId）+ 来源（块 id 或归一化选文 sha256）+ 目标语言**」键控，落盘 `translations/<docId>/<parseId>.json`（一个 parseId 一个文件，译文与解析身份天然绑定；同键覆盖更新、跨语言共存）。已有对应译文直接复用（200 `{reused:true}`，不重复调用翻译服务）；同一译文（同键）的在途请求去重（双击/并发只翻译一次）。
- **事务式保存与防污染**：翻译成功才写入（失败不产生任何落盘记录，502 明确反馈）；请求时与落盘前**双重校验 parseId 与当前页解析一致**——解析替换期间返回的旧翻译响应一律 409 丢弃，不写入新解析（配合 #9 的按页替换语义：新解析保存时旧译文不再出现在查询结果里，GET 只按当前 parseId 读取）。
- **前端（`web/translator.js`）**：译文渲染在对应内容旁（块译文紧跟该块；选文译文在包含选文的块后，找不到时列表末尾），头部标注来源（内容块/选文）、目标语言、引擎模型与复用状态（「已有译文」chip + `data-reused`），可折叠；请求中（翻译中…）与失败状态可见，失败可就地重试；打开/翻页/重开时经 GET 取回当前页绑定译文就地恢复（恢复即标注复用）。组件零耦合：仅监听 `ParsePanel` 的 `BLOCKS_CHANGED_EVENT`（detail 携带 docId/page/parseId）与内容列表点击。
- **边界**：翻译请求/取回同时作为客户端会话心跳（同 #6 语义）；未配置密钥时 503 + 界面明确提示「设置 MINIMAX_API_KEY 后重启服务」，阅读与查词不受影响；超长选文（>20000 字符）400。
